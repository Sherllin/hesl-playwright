## 首次业务运行发现的赋分阻断

用户在本地运行两条 CASE-014，均在 `paper-compose/save-draft` 返回 `10409`，尚未执行 PDF 检查。实际请求总分为 6，组合题外层分值为 2，但正文及唯一简答子题分值为 0。

根因在产品 `Paper/Score.tsx`：原条件只在子题数量大于 1 时显示子题赋分表，单子题组合只写父题分值；保存时又按零分子题汇总，导致内外分值不一致。产品修复为存在子题即显示子题赋分表，并用真实组件及保存转换验证逐题/批量设分、保存和重进再修改。桌面用例的三题、`setChildScores([2, 2, 2])` 和 `E200` 断言保持，不能增加子题或放宽返回码绕过该缺陷。

当时需由测试环境加载修复后的产品前端，再重跑 CASE-014；赋分回归通过不代表后续三种 PDF 已验收。

## 暂存后组合小题 ID 的阶段校验修正

用户后续运行已通过暂存 `E200`，各层分值均为 2，但重进时组合小题 ID 与题库 ID 不同。实际 trace 确认变化发生在保存响应，正文和答案保持；这是产品原 Java `fillCombItemId` 的既有行为：每次保存为组合直接子题分配新卷内 ID，并令 `rootId` 指向原根题。单选选项和匹配题不适用这条规则。

专项保留来源→首次保存请求的完整 ID/正文/答案校验，只在保存请求→响应之间接受组合直接子题的已知 ID/rootId 规范化，且要求十进制字符串、新 ID 唯一、根归属正确。暂存响应→重进、重进→正式提交请求、正式提交响应→审卷均严格比较身份、递归业务内容和分值，不能仅把 ID 从断言中删掉。正式提交也会再分配一次 ID，因此审卷采用该次真实响应为基线。

当时已用用户实际暂存请求、响应和重进数据离线复验通过，未新增业务登录或运行。新增离线正反例覆盖正常规范化、再次提交、读取阶段擅自改号、选项/根/更深子题改号、错误归属、非法或重复 ID、正文/答案变化、分值清零和丢题。该阶段尚待用户重跑实际全流程及 PDF 输出。
